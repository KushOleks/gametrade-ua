# GameTrade UA

Український маркетплейс ігрових цінностей на ASP.NET Core MVC (.NET 8),
Entity Framework Core 8 та SQLite. Це навчальний застосунок без реальних оплат.

## Локальний запуск

Потрібен .NET 8 SDK/runtime. З кореня проєкту:

```sh
dotnet restore
dotnet run --urls http://127.0.0.1:5189
```

На Mac з кількома версіями .NET можна явно вибрати .NET 8:

```sh
/opt/homebrew/opt/dotnet@8/libexec/dotnet build
/opt/homebrew/opt/dotnet@8/libexec/dotnet bin/Debug/net8.0/OrderSystem.dll --urls http://127.0.0.1:5189
```

Відкрийте `/Products`, `/Sellers`, `/Customers` або `/Orders`.
При першому запуску застосовуються міграції та створюються демонстраційні записи.
Замовлення можна оформити після вибору продавця та покупця. Нових продавців і
покупців можна додати через меню. Оплата і передавання ігрових цінностей не виконуються.

## База даних та EFC

- `Data/MarketplaceContext.cs` — DbContext та Fluent API для зв’язків і обмежень.
- `Data/SampleData.cs` — початкові дані лише для порожньої бази.
- `Migrations/` — версійна схема та snapshot. `EnsureCreated` не використовується.
- `Data/MarketplaceContextFactory.cs` — створення контексту для CLI міграцій.
- `Services/EfProductService.cs`, `EfUserDirectoryService.cs` — постійне сховище.
- `Program.cs` — `AddDbContext`, Scoped-сервіси, `Database.Migrate()`.
- `ConnectionStrings:Marketplace` в `appsettings.json` — за замовчуванням
  `Data Source=App_Data/marketplace.db`. Для іншого файла можна задати змінну
  середовища `ConnectionStrings__Marketplace`.

Файл SQLite зберігається локально й виключений із Git разом із WAL/SHM.
Товари, профілі, покупці, продавці та замовлення переживають перезапуск.
Старі дані з In-Memory процесу автоматично перенести неможливо; створюється
нова БД із демонстраційними даними. Попередні InMemory-сервіси залишені
як приклад Lab 2, але більше не зареєстровані в DI.

Модель для маркетплейсу адаптована зі схеми супермаркету:

```text
Seller 1 ── * Product
Seller 1 ── * Order * ── 1 Customer
Order  1 ── * OrderLine * ── 1 Product
```

Ціни зберігаються як decimal (SQLite TEXT), обчислення сум виконуються через
.NET decimal. Кожна позиція зберігає назву й ціну на момент оформлення.
Зміна каталогу не змінює історичну суму. Сервер ігнорує підставлені клієнтом
назви й ціни, перевіряє продавця, покупця, доступність та кількість 0–999.
Кількість 0 у формі означає «не додавати» / «видалити позицію»; замовлення
не може бути порожнім. У редагуванні замовлення можна змінити покупця та
кількості існуючих позицій; для додавання інших товарів створіть нове замовлення.

Товар, продавець або покупець із залежними записами не видаляється — сайт
показує пояснення. Видалення замовлення каскадно видаляє його позиції.
Товар із замовлення можна позначити недоступним замість видалення.
Дата зберігається й відображається як UTC. Версія замовлення захищає від
перезапису застарілою формою; масове редагування цін виконується транзакцією.

Міграції з CLI (інструмент зафіксовано локальним manifest):

```sh
dotnet tool restore
dotnet ef migrations add DescribeChange
dotnet ef database update
```

Для локального навчального запуску міграції також застосовуються автоматично.
Для спільного production-сервера потрібне окреме кероване застосування міграцій.

## Що належить до практичних

1. **Lab 1:** MVC, головна сторінка, MarketplaceInfoService через DI,
   RequestLoggingMiddleware, спільний темний дизайн.
2. **Lab 2:** Product, IProductService, CRUD і Razor Tag Helpers,
   server-side validation та antiforgery. Спочатку In-Memory, тепер EF Core.
3. **Практична 3:** маршрути-аліаси, GET-фільтри каталогу, власна 404,
   навчальний список користувачів: POST `/users/index` із `accessCode=df2323eoT`
   в тілі форми. Без коду — 401; без antiforgery токена в POST — 400.
4. **Validation / Binding:** ціна 0–100 000, enum-категорії, необов’язковий
   опис 3–500 символів без дублювання назви; після збереження — деталі.
   `/Products/EditPrices?category=Skins` змінює ціни всієї категорії атомарно.
   `/Users/Create?DisplayName=PlayerUA&FavoriteGame=CS2` створює демопрофіль
   тільки з query string після POST-підтвердження. Роль завжди «Користувач».
5. **EFC:** DbContext, зв’язки, SQLite, міграції, seed, Scoped-сервіси,
   CRUD покупців/продавців/замовлень, пов’язані дані, пошук покупців за
   іменем/прізвищем, сортування за прізвищем/містом у двох напрямках,
   пагінація довідників по 5 записів та незмінні ціни позицій замовлень.

Тематична адаптація: замість Supermarket використовується Seller;
замість SQL Server — SQLite для macOS; реєстрація DbContext у Program.cs
замість старого Startup.cs. CRUD написаний під наявний дизайн без scaffolding.

## Перевірки

```sh
dotnet build
python3 tests/ef_persistence.py
```

Інтеграційний тест створює тимчасову БД та окремий сервер, запускає перевірки
попередніх практичних, перевіряє зв’язки, створення/редагування/видалення
замовлень, історичні суми, захист від підміни, пагінацію та збереження даних
після двох перезапусків. Основний файл `App_Data/marketplace.db` не змінюється.
Змінна `DOTNET8` дозволяє вказати інший шлях до виконуваного файла dotnet.

`tests/smoke.py` та `tests/validation_binding.py` можна запускати проти
окремого тестового сервера. Другий створює демопрофіль QueryPlayerUA;
повторний запуск потребує нової тестової БД, а не перезапуску сервера.

## Межі поточного етапу

Демоадмін-код не є реальною авторизацією. Керування довідниками й замовленнями
відкрите в навчальному режимі. Перед публічним запуском потрібні вхід,
ролі та права власника оголошення/замовлення, резервне копіювання й платежі.
Демопрофілі та покупці поки окремі сутності, а не єдина система облікових записів.
Не використовуйте навчальну адмінчастину для справжніх персональних даних.
